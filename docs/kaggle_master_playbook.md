# Kaggle Playbook: House Prices + Titanic

Этот файл можно использовать как готовый конспект, README-документ или основу для ответа на ревью.

## 1. Общий подход к любому Kaggle-соревнованию

| Шаг | Что делаю | Зачем |
|---|---|---|
| 1 | Читаю постановку задачи и метрику | Понимаю, что именно оптимизирую |
| 2 | Смотрю на форму данных, пропуски, типы признаков и риск утечки | Не строю модель вслепую |
| 3 | Делаю простой бейзлайн | Проверяю, есть ли сигнал в данных |
| 4 | Делаю честную CV | Сравнение моделей становится валидным |
| 5 | Сохраняю OOF, сабмиты и метрики | Можно разобрать эксперименты позже |
| 6 | Добавляю фичи постепенно | Понимаю, что реально улучшает скор |
| 7 | Только потом пробую бленд или более сильную модель | Не усложняю проект без причины |
| 8 | Пишу объяснение решений | Чтобы я сам и ревьюер понимали логику |

## 2. Как я объясняю структуру проекта

| Слой | Ответственность | Почему это удобно |
|---|---|---|
| `data` | Чтение сырых файлов | I/O отдельно от логики |
| `features` | Feature engineering | Легко менять и тестировать |
| `models` | Реестр моделей и preprocessing | Понятно, что сравнивается |
| `training` | CV, OOF, blending, export | Одинаковая оценка для всех кандидатов |
| `run_pipeline` | Одна точка запуска | Ревьюеру не нужно искать вход по всему проекту |

## 3. House Prices: постановка задачи и бейзлайн

| Вопрос | Ответ |
|---|---|
| Что предсказывается? | `SalePrice` |
| Тип задачи | Регрессия |
| Метрика | Ошибка в лог-пространстве, поэтому важны относительные ошибки |
| Трансформация таргета | `log1p(SalePrice)` |
| Бейзлайн | Ridge, Lasso, ExtraTrees, CatBoost |

### Почему именно такой бейзлайн

| Модель | Что проверяет |
|---|---|
| Ridge | Есть ли стабильный линейный сигнал |
| Lasso | Насколько полезен отбор признаков и борьба с шумом |
| ExtraTrees | Есть ли нелинейные зависимости |
| CatBoost | Можно ли получить более сильный табличный ориентир |

### Почему архитектура именно такая

| Решение | Причина |
|---|---|
| Импутация чисел медианой | Просто и устойчиво |
| Импутация категорий наиболее частым значением | Стандартный табличный старт |
| One-hot encoding | Хорошо работает на средних табличных данных |
| Scaling | Полезен для линейных моделей |
| Разделение на модули | Проект легче читать и менять |
| Артефакты `reports / metrics / predictions / submissions` | Эксперименты остаются воспроизводимыми |

## 4. Titanic: постановка задачи и бейзлайн

| Вопрос | Ответ |
|---|---|
| Что предсказывается? | Survival / `Survived` |
| Тип задачи | Бинарная классификация |
| Метрика | Accuracy |
| Бейзлайн | Logistic Regression, Random Forest, ExtraTrees, CatBoost |
| Доп. режим | WCG, то есть групповые survival-эвристики |

### Почему бейзлайн такой

| Модель | Что проверяет |
|---|---|
| Logistic Regression | Есть ли линейный сигнал |
| Random Forest | Есть ли полезные нелинейности |
| ExtraTrees | Даёт ещё один деревьевый взгляд на те же признаки |
| CatBoost | Сильный табличный кандидат |

### Почему WCG вынесен отдельно

| Плюс | Риск |
|---|---|
| Использует структуру семей и билетов | Можно случайно получить утечку |
| Иногда заметно помогает Kaggle-скорингу | Может дать завышенный CV, если считать неправильно |
| Хорошо показывает Kaggle-эвристику | В проде такие признаки надо использовать осторожно |

## 5. Как я объясняю решение ревьюеру

1. Сначала я понял постановку задачи и метрику.
2. Потом собрал простой, честный бейзлайн.
3. Потом добавил feature engineering и сравнил модели под одной CV.
4. Потом сохранил OOF, метрики и сабмиты, чтобы эксперимент можно было восстановить.
5. Потом отдельно вынес рискованные эвристики вроде WCG, чтобы было видно, что это улучшение, а не базовая логика.

## 6. Краткая фраза для собеседования или ревью

Я начал с простого бейзлайна, чтобы проверить сигнал в данных, затем постепенно добавлял признаки и более сильные модели, а архитектуру разнес по слоям `data / features / models / training / pipeline`, чтобы каждое решение можно было объяснить, проверить и повторить.
